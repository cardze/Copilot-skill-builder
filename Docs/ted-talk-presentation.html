工作記憶（context window）快滿時，AI 開始緊張——倉促收尾、品質下降。就像一邊看 100 頁文件一邊寫作。

12
洞見 — Evaluator Back Force
讓 Evaluator 有真正的驗收能力
1
Adversarial System Prompt
明確告訴 Evaluator：你的工作是找錯，不是確認正確。預設假設功能是壞的，PASS 需要正面證據。
"Start with the assumption
that the feature is broken.
When in doubt, FAIL."
2
Few-shot 校準嚴格度
給 Evaluator 看「太寬鬆的 PASS」和「正確嚴格的 FAIL」的對比範例，讓它知道真正的標準在哪裡。
BAD: "button exists ✓" GOOD: "click → no response"
3
Structured Verdict Schema
強制 Evaluator 回傳 JSON，包含具體證據、重現步驟、根本原因假設。confidence < 80 一律視為 FAIL。
{ "verdict": "PASS|FAIL",
  "evidence": "...",
  "confidence": 0-100 }
4
Tool Grounding (Playwright)
不讀 code，直接操作 app。Evaluator 有真實的 click / fill / screenshot 工具，錯誤逃不掉。
page.click() → page.screenshot()
→ console_errors captured
5
負面測試案例 in Sprint Contract
Sprint contract 裡預定義 fail_criteria——讓 Evaluator 主動嘗試每一個失敗場景，不只測試 happy path。
最強一招
6
Multi-round Escalation
如果 PASS 但 confidence < 90，自動觸發第二輪對抗性檢查：「找出第一輪遺漏的問題。」
Round 1: PASS (72%) → escalate → Round 2: FAIL
13
洞見 — Evaluator Back Force
讓 PASS 很難賺到
# Sprint Contract — 預定義失敗條件
sprint_contract = {
  "feature": "Delete entity from canvas",
  
  "pass_criteria": [
    "Entity disappears after clicking Delete",
    "Ctrl+Z restores the entity",
  ],
  
  "fail_criteria": [  # Evaluator 必須主動嘗試每一條
    "Entity still visible after delete",
    "Console errors during delete",
    "Other entities affected",
    "Delete works once but not twice in a row",
    "Crash on deleting last entity",
  ]
}
重新定義「完成」
PASS 需要正面通過所有 pass_criteria，
並且主動測試所有 fail_criteria 均未觸發。
核心洞見
Evaluator 應該需要努力才能給出 PASS，
而不是需要努力才能給出 FAIL。

目前是誰在做這件事？
這些 showcase 來自 Anthropic、OpenAI、Google DeepMind 等大型 AI 公司的內部工程師——他們有優先 API 存取權、內部模型、龐大的計算資源，以及整個研究團隊的支持。
💸
真實的成本門檻
一次完整的 6 小時 harness run 花費約 $200 美元。多次迭代、多個專案、開發週期——對大多數個人開發者或小團隊而言，這還不是日常可負擔的工作流。
🔧
技術複雜度
設計有效的 sprint contracts、校準嚴格的 evaluator、整合 Playwright 測試——這需要深度的系統設計知識，不是叫 AI 寫一個 prompt 就能完成的。
這是一個方向，不是一個今天人人都能複製的食譜。
但了解這個方向，會讓你看清楚 AI 工程的下一步在哪裡。
