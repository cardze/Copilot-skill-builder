走上台，停頓三秒，環視觀眾

我想問大家一個問題。

如果今天有人跟你說——「你只需要說一句話，就有人幫你做出一個完整的軟體應用程式。」你相信嗎？

停頓

六個月前，我也不相信。

但就在今年，Anthropic 的工程師做到了——他用一句話：

「幫我做一個 2D 復古遊戲製作工具。」

六小時後，他拿到了一個有關卡編輯器、角色編輯器、AI 輔助關卡設計，還有完整遊戲引擎的應用程式。

停頓

今天，我想跟大家聊聊這件事背後的核心技術——

它叫做 Harness Design。

它不是新的 AI 模型。它不是新的訓練方法。

它是一個問題的解答：
「如何讓一個很聰明的 AI，
真正把一件複雜的事做完？」

切換投影片：Agent 感知-推理-行動迴圈

在我說 Harness Design 之前，我需要先確認大家對一個概念有共同的理解——

什麼是 AI Agent？

一般的 AI 呼叫，是一問一答。你問，它回答，結束。

Agent 不一樣。它有一個迴圈：

觀察環境 → 思考決策 → 使用工具採取行動 → 觀察結果 → 再次思考……

這個迴圈一直轉，直到目標達成為止。

停頓

而 Agent 能使用的工具，包括：搜尋網路、執行程式碼、讀寫檔案、操作瀏覽器——

還有一個最關鍵的工具：呼叫另一個 Agent。

這就帶出了今天真正的核心概念——Orchestration。

切換投影片：四種 Orchestration Patterns

當一個 Agent 不夠用的時候，你可以讓 Agent 指揮 Agent。這叫做 Orchestration Patterns，目前業界有四種主要模式：

第一種，Sequential Pipeline——像工廠流水線，A 做完交給 B，B 做完交給 C。適合有明確步驟的任務。

第二種，Parallel Workers——一個 Orchestrator 同時派出多個 worker 平行處理，最後匯整結果。適合可以拆分的大型任務。

第三種，Routing——根據輸入的性質，動態決定要派給哪個專業 Agent 處理。像一個智慧型客服中心的分派系統。

停頓

然後是第四種——也是今天的主角：

Evaluator-Optimizer Pattern

一個 Agent 負責產出。另一個 Agent 負責嚴格評估。評估結果回傳給產出者，讓它改進。這個迴圈不斷循環，直到達到明確的標準為止。

切換投影片：Evaluator-Optimizer 迴圈圖

這個 pattern 的關鍵，是分離。產出者不評估自己的作品。評估者不參與產出。

聽起來很簡單，對嗎？

停頓，微笑

但在 AI 的世界裡，要讓這個 pattern 真正有效，有一個非常根本的障礙。

讓我解釋。

🤖
Agent vs. 一般 API 呼叫
一般 API：問一個問題，得一個答案，結束。Agent：設定目標，自主使用工具，根據結果調整，持續執行直到完成——包括呼叫其他 Agent 作為工具。
🔄
四種 Orchestration Patterns
① Sequential Pipeline — A→B→C 流水線
② Parallel Workers — 同時派出多個 worker
③ Routing — 動態路由到專業 Agent
④ Evaluator-Optimizer — 產出 ⇄ 嚴格評估（今天的主角）
第一章 ・ 1:30 – 4:30
問題——為什麼 AI 會「失智」
⏱ 3 分鐘 🎯 建立問題框架
這段要讓觀眾感同身受。「AI 說自己做得很好但其實是壞的」這個場景每個人都能理解。停頓後說「但當你真的打開 app」，要帶點戲劇性。

切換投影片：AI 對話截圖，顯示自誇的回應

先讓我描述一個你可能沒想過的場景。

你叫 Claude 幫你建一個完整的 web app。一開始，它做得很好。架構清晰，程式碼乾淨，功能也一個個實作出來。

但兩個小時後——

它開始忘事了。

它忘記自己之前做了什麼決定。它開始重複做已經做過的事。它的程式碼開始出現矛盾。最後，它匆匆忙忙地「完成」了工作——然後告訴你：「這個 app 做得非常好！品質很高，功能完整！」

停頓，微笑

但當你真的打開 app 試用的時候——遊戲裡的角色動不了。

停頓

這不是 Claude 在說謊。這是兩個非常根本的問題。

🧠
Context Anxiety — 上下文焦慮
每個 AI 都有「工作記憶」上限（context window）。當快滿的時候，它會開始「緊張」——倉促收尾、降低工作品質。就像你一邊看 100 頁文件一邊寫作，頁數越多就越記不住前面的內容。
🪞
Self-Evaluation Bias — 自我評估偏差
當你叫 AI 評估自己剛做的東西，它幾乎永遠都說「不錯！」即使 app 裡的核心功能是壞的，它還是會稱讚自己。這不是 AI 特有的問題——人類改自己的作業，也會覺得比較好。
如何設計一個系統，讓 AI 能夠長時間工作，
而且能夠真正地、嚴格地評估自己的成果？
核心問題
第二章 ・ 4:30 – 7:30
洞見——從 GAN 得到的靈感
⏱ 3 分鐘 🎯 介紹核心洞見
GAN 的故事要講得生動——「在酒吧裡想到的」這個細節很重要，讓觀眾覺得偉大的想法也可以來自日常。「讓 evaluator 變得嚴格」這個轉折要放慢說。六種 back force 技術不需要逐一細講，挑 2-3 個你最有感覺的說就好，其他讓投影片帶過。最後「讓 PASS 很難賺到」這句要說得有力，它是整個 evaluator 設計的核心哲學。

切換投影片：GAN 架構示意圖

答案來自一個有趣的地方——

2014 年，一個叫做 Ian Goodfellow 的研究者，在一個酒吧裡想到了一個點子。他創造了一種叫做 GAN——生成對抗網路——的架構。

概念非常簡單：你有兩個神經網路。一個負責生成，一個負責判別。生成者想騙過判別者。判別者想抓住生成者。兩個不斷對抗、不斷進步。

停頓

Anthropic 的工程師 Prithvi 看到了這個結構，然後想到一個問題——

如果我把 AI coding agent 也設計成這樣，會怎樣？

一個 agent 負責做。另一個 agent 負責挑毛病。

停頓，讓這個概念沉澱

但這裡有一個關鍵的洞見——

光是「分開」是不夠的。因為如果你只是叫另一個 Claude 來評估，它還是會太仁慈。AI 對 AI 生成的東西，天生有一種寬容。

所以你需要做一件事：

讓 evaluator 變得嚴格。

你需要給它具體的標準。你需要用 few-shot 範例校準它的口味。你需要讓它不只是「讀 code」，而是真的去操作那個 app。

🎭
Playwright 自動化測試
Evaluator 被裝備了 Playwright——它可以自動開啟瀏覽器、點按鈕、填表單、測試每一個功能，像真實用戶一樣操作 app，然後給出精確到程式碼行數的 bug report。

切換投影片：Playwright 操作截圖

然後它會回報：

「Rectangle fill tool——FAIL。函數存在，但 mouseUp 事件沒有正確觸發。」

「Delete entity——FAIL。Handler 同時需要兩個條件，但點擊只設定了其中一個。」

精確到程式碼的哪一行出了什麼問題。

停頓

但我想在繼續之前，先說清楚一件事。

光是「讓另一個 agent 來評估」，還不夠。預設的 AI 行為是友善、是鼓勵——它天生想說好話。你需要主動地、刻意地給 evaluator 添加後坐力。

切換投影片：六種 Back Force 技術

有六種方法可以做到這件事。

第一，Adversarial System Prompt——在 evaluator 的系統提示裡明確寫道：「你的工作是找錯，不是確認正確。預設假設功能是壞的。如果你不確定，就 FAIL。」這一句話，就能把 evaluator 的基準線往嚴格的方向移動。

第二，Few-shot 校準——給 evaluator 看兩個對比範例。一個是「太寬鬆的 PASS」：「按鈕存在，看起來可以點。」另一個是「正確嚴格的 FAIL」：「點擊後沒有回應，console 顯示 null reference。」這兩個範例，讓 evaluator 知道它的標準應該在哪裡。

第三，Structured Verdict Schema——強迫 evaluator 回傳 JSON，裡面必須包含：verdict、具體證據、重現步驟、根本原因假設，還有一個 confidence 分數。如果 confidence 低於 80，一律視為 FAIL。這樣做的好處是，evaluator 必須「言之有物」，無法模糊帶過。

第四，你已經看到了——Playwright 工具接地。不讀 code，直接操作 app。讓 evaluator 真的點按鈕、填表單，捕捉所有 console error。

停頓

第五，也是我認為最被低估的一招——

在 Sprint Contract 裡預先定義失敗條件。

不只告訴 evaluator「什麼叫成功」，還要告訴它「你必須主動去試這些失敗場景」：連續刪除兩次會不會壞？刪除最後一個元素會不會 crash？刪除時其他元素有沒有受影響？

這讓 evaluator 從「等著被說服這是好的」變成「要主動去把它搞壞」。

第六，Multi-round Escalation——如果 evaluator 給了 PASS 但 confidence 只有 70%，自動觸發第二輪更嚴格的檢查，帶著一個額外指令：「找出第一輪遺漏的問題。」

停頓，環視觀眾

這六種技術的核心哲學，只有一句話：

讓 PASS 很難賺到。

Evaluator 應該需要努力才能給出 PASS——而不是需要努力才能給出 FAIL。

這才是真正的 code review。
核心突破
⚔️
六種 Evaluator Back Force 技術
① Adversarial System Prompt — 預設假設功能是壞的，PASS 需要正面證據
② Few-shot 校準 — 用對比範例定義「真正嚴格」的標準
③ Structured Verdict Schema — 強制回傳有證據的 JSON，confidence < 80 = FAIL
④ Tool Grounding (Playwright) — 真實操作 app，不只讀 code
⑤ Fail Criteria in Sprint Contract — 預定義失敗場景，強迫主動嘗試
⑥ Multi-round Escalation — 低 confidence PASS 自動觸發第二輪對抗檢查
🎯
核心哲學
讓 PASS 很難賺到。Evaluator 應該需要努力才能給出 PASS，不是需要努力才能給出 FAIL。這個方向的反轉，是整個 back force 設計的根本。

架構——三個 Agent 的分工
⏱ 3 分鐘 🎯 說明完整架構
這段是技術密度最高的段落。每介紹一個 agent，停頓讓觀眾消化。「Sprint contract」這個概念要解釋清楚——它解決了一個「做完」定義不明確的問題，這個問題觀眾都有共鳴。

Planner
把你的一句話擴展成完整的產品規格書——功能列表、技術選型、視覺設計方向、AI 功能整合計劃。它讓系統從一開始就有「野心」，避免 Generator 低估範疇。
⚡
Generator + Sprint Contract
每個 sprint 開始前，Generator 和 Evaluator 協商一份 sprint contract——「我這個 sprint 要做什麼、達到什麼標準、你要怎麼測試我。」雙方同意才開始寫 code，強迫把「做完」的定義說清楚。
🔍
Evaluator
不讀 code。打開瀏覽器，像用戶一樣操作 app，測試每一個 sprint contract 裡的標準。失敗就給出精確的 bug report 回傳給 Generator。這個迴圈一輪一輪轉，直到每個標準都通過為止。

停頓

但故事沒有結束。

隨著 Claude Opus 4.6 推出，工程師發現了一件有趣的事：很多原本 harness 負責解決的問題——context anxiety、sprint 分解——新模型自己就能處理了。

結果呢？最終的 DAW app——一個完整的瀏覽器音樂製作軟體——你可以在裡面建鼓組、加旋律、調混音、加 reverb，然後叫 AI 幫你一鍵生成一首歌的框架。

停頓，環視觀眾

💡
關鍵洞見：Harness 不是永恆的
Harness 的設計，本質上是一組「模型做不到什麼」的假設。隨著模型進步，這些假設會過期。好的工程師需要不斷問自己：這個組件現在還 load-bearing 嗎？還是模型已經自己能做到了？
第五章 ・ 12:30 – 14:30
更大的啟示——結構才是品質的來源
⏱ 2 分鐘 🎯 普遍化道理
這段要從技術跳到哲學。每個類比——code review、期刊審查、手術室 checklist——停頓一下讓觀眾消化。最後的大結論要說得有力、放慢速度。

我想在結束之前，說一件更大的事。

這個 harness 的故事，表面上是一個技術架構的故事。但更深層，它告訴我們一件關於「系統設計」的普遍道理。

👩‍💻
軟體公司
有 code review、QA、staging 環境、design review。每一個環節都在說：我不相信任何人能完美地評估自己的工作。
📚
頂尖學術期刊
有雙盲審查。你不知道作者是誰，作者不知道你是誰。讓評估者保持嚴格、中立。
🏥
頂尖手術室
有 checklist。即使是世界最頂尖的外科醫生，也需要在開刀前逐項確認——不是因為他不夠聰明，而是因為結構保護所有人。
結構，才是品質的來源。
不是個人的天才。
核心主張

而 harness design 做的，就是把這個道理，應用到 AI agent 身上。

它說：不要只是叫 AI 更努力。

要給 AI 一個更好的工作環境。

讓它能夠被檢查、被挑戰、被迫清楚地定義「完成」是什麼。

結語 ・ 14:30 – 15:00
設計環境，釋放潛力
⏱ 0.5 分鐘 🎯 留下深刻印象

我們正在進入一個很奇妙的時代。

AI 的能力在快速增長。但「讓 AI 真正完成複雜任務」這件事，不只是模型的問題——

也是系統的問題。
也是設計的問題。

Harness design 告訴我們：最有趣的工程問題，不是「模型有多強」，而是——

你怎麼設計一個環境，
讓它能夠發揮出真正的潛力？
留給觀眾的問題
